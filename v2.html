Old: url.Split("/") allocates a string[] + each element is a heap string; wrapping in .AsEnumerable().GetEnumerator() adds an IEnumerator box. For a 5-segment path that is roughly 7 heap objects per call.

New: url.AsSpan() is zero-allocation; MemoryExtensions.Split (C# 13 / .NET 9+) returns SpanSplitEnumerator<char> as a stack-only value type — zero heap allocations. The Dictionary.GetAlternateLookup<ReadOnlySpan<char>> (new in .NET 9) lets the trie lookup proceed on the span slice without materializing a new string.

Find() — ArrayPool replaces List<T>

-var urlPattern = new List<string>();
-// ... build lists ...
-return (urlPattern.ToArray(), urlParams.ToArray());
+var patternBuffer = ArrayPool<string>.Shared.Rent(16);
+var paramsBuffer = ArrayPool<object>.Shared.Rent(8);
+// ... fill slices ...
+finally {
+ ArrayPool<string>.Shared.Return(patternBuffer, clearArray: true);
+ ArrayPool<object>.Shared.Return(paramsBuffer, clearArray: true);
+}

Old: two List<T> allocations, each backed by an internal array that may resize (doubling alloc), plus two final .ToArray() copies. Minimum 4 heap objects even for a single-segment path.

New: borrows from ArrayPool.Shared (warm, pooled). Only the final result array is heap-allocated. For zero-parameter paths, the paramsBuffer path returns the cached empty array [] — no allocation at all.

IsPathParam / IsQueryParam — char comparisons, AggressiveInlining

-private static bool IsPathParameter(string key) =>
- key.StartsWith("{") && key.EndsWith("}");
-private static bool IsQueryParameter(string key) => key.StartsWith("?");
+[MethodImpl(MethodImplOptions.AggressiveInlining)]
+private static bool IsPathParam(ReadOnlySpan<char> segment)
+ => segment.Length >= 2 && segment[0] == '{' && segment[^1] == '}';
+[MethodImpl(MethodImplOptions.AggressiveInlining)]
+private static bool IsQueryParam(ReadOnlySpan<char> segment)

Old: string.StartsWith(string) triggers a virtual dispatch + ordinal scan. New: direct char indexer comparison — single instruction on x86/ARM, no virtual call. AggressiveInlining eliminates the method call overhead entirely on the JIT hot path.

URL segments are always ASCII; StringComparer.Ordinal avoids culture-aware comparison overhead (~10-20% faster dictionary lookup on URL-shaped keys) and is the correct semantic for HTTP paths.

2. InMemoryEndpointGraph.cs — Thread Safety Fix (Critical Bug)

Libraries/EndpointGraphs/EndpointGraph.InMemory/InMemoryEndpointGraph.cs
ReaderWriterLockSlim ✓ static → instance field ✓ IDisposable
Race condition fixed Was: data races on every request Static field removed → DI-lifetime safe
-private static EndpointNode _patternTree = EndpointNode.CreateRoot();
+private EndpointNode _patternTree = EndpointNode.CreateRoot();
+private readonly ReaderWriterLockSlim _rwLock = new(LockRecursionPolicy.NoRecursion);
Critical bug fixed The old private static EndpointNode _patternTree was shared across ALL instances (and effectively across all requests) without any synchronization. ClearAsync() replaced the reference, while concurrent readers could still hold the old tree — or worse, partial tree writes from Append() could be observed by concurrent readers. This is an unguarded race condition.

ReaderWriterLockSlim is the right tool here: many concurrent read-only lookups (every gateway request) vs infrequent writes (startup / config reload). Under read-heavy load (the common production case), readers never block each other — only writes take an exclusive lock.

+public ValueTask<(string?, object[])> FindAsync(...)
+{
+ _rwLock.EnterReadLock();
+ try { return ValueTask.FromResult(_patternTree.Find(url)); }
+ finally { _rwLock.ExitReadLock(); }
+}
Trade-off to note ReaderWriterLockSlim is a kernel-level synchronization primitive. Under extremely high core counts (32+ cores) with near-zero write frequency, a lock-free approach (e.g., Volatile.Read on an immutable tree + atomic swap on write) could be marginally faster. For typical gateway deployments (4-16 cores, startup-time writes only), RWLS is the correct practical choice.

4. HttpClientExtensions.cs — MemoryStream Eliminated

Core/Extensions/Http/HttpClientExtensions.cs
✓ MemoryStream removed ✓ using on HttpRequestMessage
Per file upload: 1 MemoryStream + buffer removed HttpRequestMessage disposed correctly
-var memoryStream = new MemoryStream();
-await formFile.CopyToAsync(memoryStream).ConfigureAwait(false);
-memoryStream.Position = 0;
-var streamContent = new StreamContent(memoryStream);
+var streamContent = new StreamContent(formFile.OpenReadStream());

Old code copied the entire file into a MemoryStream (doubling its memory footprint at peak), then seeked back to 0. Streaming directly from formFile.OpenReadStream() pipes the file content to the outgoing HTTP request without buffering it fully in memory — critical for large file uploads.

Behavioral note OpenReadStream() may need to be seeked for retry scenarios. Since the upstream code doesn't retry, this is fine here. If retries are added in future, the stream must either be re-opened or buffered. The old approach was safer for retries but wasteful for the common case.

Additionally, using var httpRequest = new HttpRequestMessage(...) ensures the request and all its HttpContent children (including the multipart stream) are disposed after the call, preventing native handle leaks.

Trade-offs & Regressions to Watch

RWLS adds lock overhead on every FindAsync() Under extremely high read-concurrency (tens of thousands of concurrent requests per second) on many-core machines, RWLS can become a contention point. If profiling shows lock contention, consider a copy-on-write approach: keep a volatile reference to an immutable EndpointNode tree; swap atomically on write.
ArrayPool with clearArray: true has a cost Returning with clearArray: true zeroes the buffer before returning it to the pool, which is correct (avoids reference leaks for the object[] params buffer), but costs one Array.Clear call per return. For the string[] pattern buffer, clearing is only needed if it holds live references — consider whether false is safe for the pattern buffer.
FastEndpoints major version jump (5 → 8) Three major versions may include breaking API changes. The codebase appears to compile (build artifacts present), but integration tests should be run to confirm behavioral equivalence.
No BenchmarkDotNet tests found No *Benchmark* or *Perf* files were located in the repository. The improvements above are analytically estimated from code patterns. Adding BenchmarkDotNet micro-benchmarks for EndpointNode.Find() would quantify the gains precisely and guard against regressions.
